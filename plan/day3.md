## 本阶段工作方式：让 AI 实现功能，你负责授权与验收

Day 3 的主要产出是可运行的代码增量和证明需求的测试，不是 AI 生成更多计划、Prompt 或可追溯文档。每个功能步骤默认要求 AI 先检查当前代码，再提出简短实施方案；你确认范围后，AI 直接修改实现和测试。只有平台账号准入、授权、迁移执行、真实渠道测试等必须由你操作的部分才由你亲自完成。handoff 只在功能或验证实际发生后补充简短证据，不以写文档替代实现。

### 功能开发 Prompt 的必要信息

让 AI 开发前，任务描述要让它能够开始写代码，而不是止于分析报告：

1. **目标**：这次要交付的最小可运行功能是什么？明确用户行为和完成条件，不用“研究/整理”代替功能目标。
2. **现状**：要求 AI 先读取相关实现、模型、迁移、测试与配置，基于当前代码定位改动点。
3. **约束**：列出已确认规则及不可做事项，例如客户负责平台准入、系统负责安全连接、三渠道连接入口、当前不做真实出站、运营主动发送、内部 AI 只读。
4. **实现授权**：明确允许 AI 修改哪些代码、测试、迁移文件。默认可直接实现；如确有数据破坏、平台准入或设计决策等需用户决定的问题，AI 先停在该边界，不要把整个任务退化为长篇方案。
5. **测试与交付**：要求 AI 编写正反向测试、运行其可运行的本地自动化测试，汇报具体命令/结果和未覆盖项；你亲自运行数据库迁移、目标环境测试和真实渠道验证。

可直接复用的任务开场：

> “请先检查当前代码和测试，然后实现【明确的用户行为/功能】。你可以修改【限定代码/测试/迁移路径】并直接补齐必要实现，不要只输出计划或文档。遵守【列出约束】；对确需我决定的未知项先提问，不要虚构。为正常、拒绝和失败场景添加测试并运行本地测试。最后给出改动文件、关键行为、测试命令/输出、我需要亲自执行的迁移/真实环境验收及尚未覆盖的边界。不要读取或输出秘密，不要替我进行生产数据修改、外部账号授权、真实发送或远程 Git 操作。”

### 审核 AI 结果的固定步骤

- 先读 AI 给出的改动摘要，再检查 `git diff` / `git diff --check`，逐文件确认改动与任务边界一致；检查没有密钥、真实客户内容、无关重构或意外依赖。
- 数据模型/迁移：读迁移的 upgrade/downgrade，确认只改本次需要的表/索引/约束；先审阅再由你运行迁移，并检查实际数据库 revision/schema。
- 授权/渠道：检查授权发生在读取对象前；客户完成平台准入/授权，系统安全保存凭据并按客户账号隔离；不要求前端粘贴长期 Token；发送只能由运营主动触发；内部 AI 不含写操作；Webhook 来源校验及渠道账号作用域没有被跳过。
- 测试：看断言是否证明需求而非仅调用成功；检查正常、拒绝、重复、失败边界；亲自运行命令并记录实际输出。AI 生成的测试通过也不等于真实 provider 账号已接通。
- 若改动涉及数据删除、迁移、真实账号授权/发送或远程 Git 写入，先审阅计划和目标，再由你明确确认并亲自执行。

终端命令（测试、Compose、迁移及 Git 操作）和真实账号授权/收发由你执行。AI 可以完成经你授权的代码编辑，但不能把“已编辑”或“测试写好了”当成验证通过。

| 功能增量 | AI 负责实现 | 你负责验收 |
|---|---|---|
| 数据库与授权基础 | 补缺失的 migration、最小授权逻辑和自动化测试 | 只读确认目标库；审阅并亲自执行 migration；检查 schema/revision 和测试输出 |
| 渠道连接中心 | 前端入口/状态、后端连接 API、客户/账号隔离、凭据安全服务与测试 | 账号所有者完成平台侧应用配置/OAuth；亲自验证已获准账号的真实入站 |
| 统一消息入库 | 消息/附件模型、migration、adapter mapping、数据库幂等 service 与测试 | 审阅 migration；应用后检查目标 PostgreSQL 约束与重复消息结果 |
| 抓取/Webhook/后台处理 | 对实际可用 provider 实现入站路径、验证和失败恢复及测试 | 账号授权；自有测试数据真实入站；确认平台阻塞如实显示 |
| 失败修复 | 补重复、并发、限流、DB 错误、撤销授权等测试，发现缺陷时直接修复并加回归测试 | 审阅 diff、运行测试；不做当前阶段真实出站发送 |
| 版本交付 | AI 可协助检查 diff、建议提交范围 | 你决定并执行 stage/commit/push/PR/merge；不提交或推送未确认内容 |

本阶段重点是让 AI 在明确范围内实际完成代码和测试增量，你通过审阅 diff、运行测试及亲自操作目标环境验收。Prompt 是启动实现的简短工具，不是 Day 3 的主要交付；不要求每个功能先产出独立的资料报告或方案文档。

## 步骤 1：确认数据库起点并让 AI 补齐迁移

### 这一步要交付什么

先由你完成最少量只读探测，确认目标 PostgreSQL 可用及当前 revision/schema。Day 1/2 的 Compose 和 `.venv` 测试基线不重复执行。之后 AI 读取当前 ORM、Alembic 配置、revision 和认证代码，直接补齐用户/会话 migration（如仓库仍缺失）及相应迁移测试；不得停留在现状报告。数据库目标和迁移破坏性必须由你审查并亲自决定是否执行 migration。

### 给 AI 的开发任务

> “请检查当前 SQLAlchemy 模型、Alembic 配置/versions、认证代码和测试。若 PostgreSQL 用户/会话 migration 或迁移测试缺失，请直接实现最小必要 ORM/migration/tests，遵循现有认证行为，不添加未确认的权限表或无关 schema。先简短列出将修改的文件和 migration 影响；如存在删表、数据丢失或目标不明确，暂停并询问。不要读取 `.env`/输出连接串，不连接真实数据库，不运行 migration。完成后运行本地相关测试，汇报命令、结果、upgrade/downgrade 行为和我需要亲自执行的数据库检查。”

### 你亲自核验与审核 AI 实现

1. 使用安全环境配置确认 Compose 指向目标库，再执行 PostgreSQL ready、应用级只读 `SELECT 1`、Alembic current 和只读 schema 查询；不要打印秘密。
2. 审阅 migration 的 upgrade/downgrade、表/索引/约束和现有数据影响。确认目标库与备份后，由你亲自执行 migration 并重新查询 revision/schema。
3. 检查 AI 的模型、migration、测试 diff，确认没有删改认证行为、无关表或凭据；运行 AI 给出的测试命令并记录实际结果。
4. 不得以 Compose 配置、迁移文件存在或旧 handoff 替代当前数据库证据。不要使用 `down -v` 清理数据卷。

### 验收标准

- 迁移代码与测试已由 AI 实际修改并通过本地测试；迁移文件经你审阅后，由你确认目标库并亲自应用。
- PostgreSQL ready、应用级只读连接、Alembic revision/schema 均有本轮输出证据；不记录秘密。
- 仅把必要命令、退出状态、迁移结果和阻塞简短记入 `day3-verification.md`；不另行撰写数据库“现状报告”。Day 1/2 的历史记录维持原样。
- 已有 `15 passed, 1 warning` 是 Day 1/2 测试基线，不重复冒充本轮结果；代码变化后运行相关测试并报告真实输出。

## 步骤 2：让 AI 实现并测试首期最小授权

### 本步骤要交付什么

在用户/会话迁移已有可用基础上（若步骤 1 发现缺失，则先完成 migration），由 AI 直接实现首期最小后端授权和测试，而非仅提供授权方案。限定范围为：运营仅访问已授权渠道账号消息；业务员只读本人被转交的原始资料和链路状态；内部 AI 的查询按发起用户权限过滤且只读。不要扩展为未来完整部门/经理/节点权限矩阵。

### 给 AI 的开发任务

> “读取现有认证、模型、路由、数据查询和测试代码，以及 PROJECT_SPEC 首期授权规则。直接实现首期最小授权：运营按已授权渠道账号过滤；业务员仅能读取分配给本人的转交资料和链路状态；内部 AI 所有查询沿用发起人权限且只读。授权必须在对象读取前执行。请修改必要的后端实现和测试，不要只返回分析报告；不改变既有登录行为、不实现未来部门/经理权限、不读取 `.env`/凭据、不连接数据库或运行 migration。覆盖未认证、允许访问、跨用户/跨渠道拒绝及只读限制；运行本地测试并汇报命令、结果、改动路径和未覆盖场景。若仓库缺少确定这些规则所需的数据模型，先指出具体缺口并询问，不要臆造 schema。”

### 你如何验收

1. 审阅授权是否在对象查询前执行，运营范围是否绑定账号，业务员是否只能读取本人转交数据，内部 AI 是否没有写操作。
2. 检查测试数据确实构造不同用户与渠道，断言拒绝结果和数据未泄露，而非只测 HTTP 成功。
3. 运行相关测试并查看实际输出。数据库 migration 仍由你审阅并亲自运行；测试不能替代目标 PostgreSQL schema 核验。

### 完成记录

记录测试命令/结果、迁移/schema 证据及未覆盖项到 `day3-verification.md`；不记录凭据或客户内容。

## 步骤 3：AI 实现渠道连接中心与账号隔离

### 本步骤要交付什么

AI 直接开发可运行的连接中心，而不止整理三份指南：前端展示 WhatsApp、Gmail、Outlook 的连接入口与状态；后端提供授权流程/连接器边界、按客户账号隔离的凭据管理、连接测试、重新授权和断开能力。真实 provider 授权依赖客户账号资格，不能假设三者都能在当前环境启用。实现顺序依据当前可用 OAuth/provider sandbox；不可用渠道先实现接口与可测试的 provider-independent 逻辑，标明准入阻塞，绝不把模拟连接显示为真实成功。

客户/账号所有者负责平台资格、应用/业务资产设置和授权；AI 不得索取密码、验证码、client secret 或 token，不得替用户登录或绕过地区/平台限制。正在 Business App 使用的 WhatsApp 号码不得未经管理员确认迁移/切换。

### 给 AI 的开发任务

> “检查当前 frontend/backend 结构、认证方式和测试设施。直接实现渠道连接中心的最小可运行增量：渠道列表/连接入口/连接状态（未连接、授权中、已连接、阻塞/错误）、后端连接状态 API 与 provider adapter 接口、凭据服务边界和客户/渠道账号授权检查。按现有项目风格修改必要前后端文件和测试，不要只写设计文档或操作指南。默认用 mock/fake provider 测试状态转换，mock 必须显著标记为测试、不能伪装真实已连接。未经批准不得存储明文 token；不得将长期 token 放入浏览器存储、URL 或日志。先实现可验证的内部连接中心和 provider-neutral 层；OAuth 集成仅针对已确认可用且官方流程清楚的 provider。不要登录账号、请求凭据、执行真实授权、迁移 WhatsApp 号码、发送消息或运行数据库 migration。补正常、拒绝、失效/撤销和错误路径测试，运行本地测试并给出我亲自配置 OAuth/验证入站的步骤。”

### 如何审阅代码并推进真实 OAuth

1. 先看代码 diff 和测试：连接状态是否后端权威、账号隔离是否发生在凭据读取前、断开/撤销是否不会误删历史消息；界面是否能区分 mock、未授权、平台阻塞和真实连接。
2. 凭据不能出现在前端持久存储、URL、日志或测试快照；后端凭据保护方案须实际实现并测试，不接受仅在文档承诺“加密”。若尚无安全密钥管理/加密实现，先让 AI 实现所需服务和测试，不接收生产 token。
3. 对可用的 Gmail/Outlook 测试应用，AI 可在用户确认配置后实现 OAuth callback、state/CSRF 校验、最小 scope、token refresh 与撤销处理；客户亲自创建应用并授权。WhatsApp 若平台准入不可用，仅实现 adapter seam 和阻塞状态，不制造真实 OAuth 成功路径。
4. 你亲自运行前端/后端测试；之后用自有测试账号完成授权和入站连接验证。当前阶段不发送任何真实出站消息。

### 验收

- 可在工作台查看三渠道状态，能进入连接/重新授权/断开流程；后端对账号状态与权限做校验。
- 自动化测试覆盖状态流转、跨账号拒绝、未授权、授权撤销/失效和凭据不泄露。真实 OAuth/入站结果按渠道分别记录；测试 mock 不得标为真实连接。
- 连接入口、指南可用性、平台账号资格、客户授权、系统 OAuth 完成、真实入站成功是不同状态，不能合并成一个“完成”。项目最终阶段另验运营主动出站。
- 只在功能/测试发生后将摘要和非敏感结果补入 `day3-verification.md`；不先制作长篇资料包。

## 步骤 4：AI 实现统一消息模型与入库幂等

### 如何构思开发 Prompt

本步骤要求 AI 从现有 ORM、migration 和需求出发，直接实现最小消息模型、migration、统一入库服务及测试。先简短指出关键字段/唯一键假设；如某个 provider 的 ID 语义未知，用账号隔离的 adapter 边界保留待验证项，不臆造，也不因此只交分析报告。

可使用这样的开发请求：

> “检查当前 ORM、Alembic migrations、测试和 PROJECT_SPEC 的消息存储要求，直接实现最小消息模型、migration、统一入库服务和测试。至少支持渠道账号隔离、外部消息 ID、方向、状态、时间戳、原始内容与附件 metadata；具体字段按代码和已核实 provider 资料确定。未知 ID 作用域不得臆造：隔离该 provider 特有实现并标记待验证，但继续实现有依据的通用部分。不要增加报价、合同、Agent 节点或部门作业表；不要读取秘密、连接目标数据库或运行 migration。覆盖首次写入、重复写入、冲突与事务失败，运行本地相关测试并汇报结果、migration 影响和我需亲自执行的数据库验收。”

### 如何审核 AI 的结果

检查每个字段是否有业务需求或 provider 数据依据；邮箱字段不要硬套 WhatsApp，原始消息不要误作 RAG 文档。审阅 AI 已实现的模型、migration、入库服务和测试；核对唯一约束是否隔离渠道账号并防重复。provider 语义未知时要求隔离实现并标待验证，不接受只给 schema 分析或“设计合理”的结论。

### 实现原则

项目定义了消息必须保留的信息，但没有完整 schema。AI 在检查当前模型后应实现最小必要结构，不先产出长篇 gap-analysis 文档。外部 ID 作用域未知时不得猜测；将对应 provider 适配器隔离并保持未验收，同时继续实现已有依据支持的公共 schema、入库服务和测试。

### 可直接交给 AI 的实现任务

> “检查当前 ORM、migration 和测试后，直接实现 PROJECT_SPEC §4.3 所需的最小消息表、附件 metadata 结构、渠道无关入库服务、唯一约束和测试。消息至少保留渠道账号、外部消息 ID、方向、状态、时间戳、原始内容及必要附件 metadata；仅添加有需求依据的字段，不加报价/合同/Agent/部门作业模型。唯一约束需按渠道账号隔离。若某 provider 的 ID 作用域或关联语义未知，列出具体假设，在 adapter 层隔离该部分，不声称真实渠道验证通过，也不要因此停止公共模型实现。直接修改必要模型、Alembic revision、service 和 tests；不要读秘密、连接目标数据库或运行 migration。运行本地测试，汇报测试输出、migration 的 upgrade/downgrade 和我需亲自执行的数据库步骤。”

AI 需要快速说明无法安全决定的字段/关联，只有会导致不可逆 schema 决策时才暂停询问；一般未知通过隔离适配器与待验证测试处理，不能把工作退化为文档审查。

### 为什么这么做

不同 provider 的 ID 作用域可能不同，因此实现须以账号为隔离边界并通过数据库约束验证幂等。未知 provider 细节应限制在该 adapter 中，不阻塞消息模型、入库服务和测试的实际开发。

### 如何审核 AI 的实现

检查代码与测试是否落实最低消息字段、渠道账号隔离和数据库级幂等；查看 migration upgrade/downgrade 与事务边界。确认未知 provider 语义没有被臆造成事实，并且不阻塞通用实现。你审阅 migration 后亲自应用，并验证 PostgreSQL schema；AI 负责实现与本地测试，你负责目标数据库变更和真实环境验收。

### 验收

- AI 已实现模型、migration、入库 service 和自动化测试；不是只交 schema 方案。
- 测试证明新消息可入库、重复消息不重复持久化、账号作用域隔离及失败时事务行为。
- 你审阅并亲自应用迁移，检查 revision、表、索引和约束。数据库未通过时只报告阻塞，不把单测称作持久化验收。
- 只在 `day3-verification.md` 简要记入实际代码路径、测试结果和数据库验收证据，不维护重复的手工记录模板。

## 步骤 5：打通已实现 schema 的渠道映射与入库服务

### 这一步交付什么

在步骤 3 的 schema/migration 已实现并经你应用后，由 AI 直接完成各 adapter 到统一消息对象的映射、入库 service、数据库冲突/重复处理，以及必要附件 metadata 保存。不要重复生成 schema 设计文档；如果步骤 3 实际缺少某个模型/字段，AI 修改代码并补 migration/test。真实 provider 未获准时以 fake provider 测内部路径，清楚标记不是真实连接。

### 给 AI 的实现任务

> “读取当前渠道 adapter、消息 ORM、migration、测试和 service 代码，直接打通【可用 provider 或 fake provider】到统一入库路径：转换渠道消息、保存原始内容和附件 metadata、按渠道账号及外部 ID 幂等写入、正确处理唯一冲突和事务失败。补首次写入、重复投递、不同渠道账号、缺失附件 metadata、DB 错误的测试；不要用进程内缓存替代数据库约束。只改必要实现与测试；不读取秘密、不访问真实账号、不运行 migration、不发送出站消息。运行相关本地测试并汇报实际结果、尚未覆盖的真实 provider 行为。”

### 审核与验收

- 检查 provider 原始字段只在 adapter 层转换，未知 ID 语义不硬编码；数据库唯一约束和事务处理支撑跨请求/并发幂等。
- 测试断言数据库最终记录数、冲突结果和失败事务状态，而不只是函数返回成功。
- 你确认 schema migration 已应用并核验 PostgreSQL；若未应用，标为阻塞，不把 SQLite/mock 单测写成数据库验收。
- 只在实现或验证实际发生后，将测试结果、迁移结果和明确未覆盖项简记入 `day3-verification.md`。

## Git 版本管理：功能分支、增量提交、推送与合并

版本控制贯穿 Day 3，不是阶段末尾的可选总结。代码以功能分支开发；**每个可独立审阅、测试通过的最小 MVP 增量完成后，就应形成一个聚焦提交**，不必等所有渠道和整个 Day 3 全部结束。提交是本地历史记录；推送用于备份/协作；PR 用于审阅；合并将已审阅变更整合回确认的基线，四者不可混为一谈。

### 1. 开始新功能前：核对并建立分支

1. 由你运行 `git status --short --branch`、检查当前 diff 和仓库基线，逐项识别现有改动。当前工作区文件此前显示未跟踪且无提交历史；先核对本地/远程分支和初始基线，不能假定 `main`/`master` 或直接把所有未跟踪内容纳入提交。
2. 对一个独立功能（如 Day 3 数据库基础、统一消息模型、单一渠道适配器）建立一个描述清楚的功能分支。分支应从你确认的开发基线创建；不要把多个互不相关的大功能塞进同一分支。
3. 如果尚无可确认基线，先整理/确认首次基线提交范围；排除 `.venv`、`.env`、密钥、本机配置、缓存和构建产物。不要使用 `git add .` 盲目暂存。

### 2. 功能推进中：最小可验证增量即提交

- 先定义该增量的可观察验收条件，再实现最小 MVP。例如：migration 可在目标 PostgreSQL 应用且 schema 可查；统一消息映射有单测；某渠道适配器有可重复测试；真实接收链路则需账号授权和实际消息证据。
- 每次达到**可运行/可测试、差异聚焦、无秘密、测试通过或已解释已知失败**的独立检查点时，逐路径暂存并审阅 staged diff，运行相关测试，然后由你亲自创建本地 commit。无需等待整个功能/阶段结束。
- 不可验证、测试失败或含秘密的改动先修复，不为保持“每天有提交”而制造无效提交。提交信息描述真实代码行为；模拟渠道提交不得声称真实接入完成。

### 3. 何时推送

- 本地 MVP 提交完成并经你检查后，若需要远程备份、跨设备协作或远程 CI/审阅，就及时推送该功能分支；**不必等 Day 3 完成**。
- 推送前确认远程仓库、目标分支、公开范围和提交内容，确保无凭据/客户敏感数据。用户亲自运行 `git push -u <remote> <feature-branch>` 或后续普通 push；远程拒绝、认证失败或非快进时先检查，不强推、不改写共享历史。
- 未确认远端/公开范围时可先本地提交，推送待确认；不得把“不推送”写成每阶段默认规定。

### 4. 何时开 PR 与合并

- 功能分支已推送且具备可审阅的 MVP（必要测试通过、差异清晰、未决项诚实标注）后，可开 PR 请求审阅；若功能仍需继续迭代，也可在同一 PR 继续追加小提交。
- PR 检查和审阅完成、目标分支明确、冲突处理完毕后，由你确认并亲自合并；需要时采用 squash/merge commit 等策略须遵从仓库规则。合并后在目标分支验证适当测试。
- 有未完成的功能不妨碍提交/推送已独立完成的增量，但不应把未完成范围描述为整体交付；未经检查的失败测试不能标绿。

### 5. 本项目 Day 3 建议切分

候选独立分支/增量可包括：`day3-db-auth`（迁移、最小授权与测试）、`day3-channel-connection-center`（可运行连接 UI/API、凭据保护与状态测试）、`day3-message-ingestion`（schema、入库幂等与测试）、每个获准 provider 的真实入站 MVP。分支切分依据可独立运行/测试的代码功能，不以资料调查或交接文档为增量。真实账号准入未完成时，连接 UI/内部 fake-provider 测试可验收为产品内部功能，但不得描述成真实渠道接通。
