## 今天的完成标准

Day 2 的数据库路径必须按以下顺序推进：确认数据库目标/提供方式 → 准备并启动所选数据库 → 验证数据库已就绪 → 配置并验证 FastAPI 应用级连接 → 定义最小身份模型 → 创建并应用 Alembic 迁移 → 检查实际 schema。之后验证认证与 RBAC。任何阶段未完成，都如实标记阻塞/待执行，不声称 Day 2 全部完成。

1. 数据库目标及提供方式有用户确认的依据；未确认时标为待确认，不自行选用 Compose。
2. 所选数据库服务按实际方式准备、启动，并有“数据库可接受连接”的证据；不能只记录进程/容器运行。
3. 后端能够安全读取配置并建立 PostgreSQL 应用级连接；实际连接结果有记录。
4. 用户、角色、权限及必要关系的 SQLAlchemy 模型和 Alembic 迁移已按确认范围建立；迁移应用和 schema 检查均有实际证据。
5. 登录认证与至少一个受保护的后端资源有实际验证；未认证请求被拒绝。
6. 后端授权验证覆盖已确认的节点负责人、经理负责范围、管理员权限和越权拒绝；不得把策略测试说成完整节点工作流。
7. 拒绝原因在后端受控记录、外部响应脱敏；Cookie/CSRF/过期等按已确认方向和实际设计验证，未决参数继续标出。
8. 数据库准备、应用连接、迁移、认证授权和测试结果分开记录；不记录密码、Token 或连接串。

认证/权限矩阵的已确认设计和剩余待定项见 [PROJECT_SPEC.md §3.1](../PROJECT_SPEC.md#31-已确认的授权设计尚非实现) 与 [architecture.md §5.1](../docs/architecture.md#51-已确认的认证与授权矩阵设计)。数据库配置、服务运行、数据库就绪、应用连接和迁移/schema 仍须分别以当前实际证据核验；任一层未执行或未通过，不得记为已验证。

## 步骤 3：准备并验证所选数据库服务



### 这一步要消除的不确定性是什么

在验证 FastAPI 前需有可用数据库。历史起点所称 Compose 只有 backend 已过时；当前以仓库 Compose 文件和目标服务器当次输出为准。服务运行不等于数据库就绪，且两者都不证明 FastAPI 已连接。

### 你手动执行的准备与核验流程

按步骤 2 已确认的数据库方式，只执行对应分支。下列流程及命令均由你手动运行，不是完整可复制脚本；方括号占位项必须替换为你确认的真实服务名/配置值。不要在命令参数、历史记录或共享截图中暴露凭据。

1. **准备配置**：若选 Compose，由你按已确认的 PostgreSQL 版本、数据库/用户、持久化策略和仅本机/内部网络访问要求，手动编辑 `compose.yaml`；如果用外部/本机数据库，则确认服务端与数据库已由管理员/你按对应方式配置。确认 secret 的安全注入来源，不把值提交到仓库。
2. **检查配置**：Compose 分支在项目根目录手动运行 `docker compose config`，确认配置能解析；这只证明语法/配置可读，不证明服务运行或 DB 就绪。非 Compose 分支按对应管理工具检查实际服务配置。
3. **启动服务**：Compose 分支根据实际服务名手动运行 `docker compose up -d [你确认的数据库服务名]`；本机服务按所选服务管理器启动；外部库由你/管理员确认服务已启动。命令中的方括号内容不是字面参数。若依赖已确认的变量文件，先按实际配置安全加载；不要因为现有 compose.yaml 有 backend 就把它当成 PostgreSQL 服务。
4. **核验运行状态**：Compose 可手动查看 `docker compose ps [你确认的数据库服务名]`；本机或外部服务使用该环境对应的服务状态工具。记录输出与退出状态，但不要把“running”当成数据库可连接。
5. **核验数据库就绪**：使用对应 PostgreSQL 客户端或项目配置的就绪检查，在安全读取凭据的前提下，实际建立一次连接/执行只读探测。确认目标地址、数据库和账号正确；不得把密码回显或把 `DATABASE_URL` 原文写进记录。仅在探测成功后将 DB 标为“已就绪”。

如果任何一步失败，记录实际错误摘要并停在该层；不要继续配置 FastAPI 或写迁移，也不要用 `/health` 200 替代 DB 就绪证据。

### 从实际选项推导手动命令 Prompt

若步骤 2 的选择已确定、但你不清楚相应运维命令，AI 可以根据你提供的非敏感配置帮助解释/整理命令模板。此时已知的是数据库提供方式和当前配置；未知的是环境里的服务名、变量文件、就绪探测入口。猜错可能启动/连接错误的服务或泄露凭据，因此 Prompt 应只要求核对你给出的值、标出占位项和预期输出，不让 AI 假设缺失值或执行操作。你逐项对照当前配置，手动替换占位并运行，再以实际输出判断服务状态与数据库就绪。

## 步骤 6：实现登录与后端 RBAC 最小闭环



### 这一步要消除的不确定性是什么
