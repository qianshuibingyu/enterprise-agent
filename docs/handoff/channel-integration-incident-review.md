# 真实渠道接入问题复盘

本文记录本轮真实环境中出现的问题、证据和验证状态，目的是改进渠道接入质量，不包含账号、邮件内容、凭据或完整 OAuth 链接。代码完成、隔离测试通过和真实环境验收通过是不同的状态。

## 1. 事件与证据

### Outlook 主动读取 Inbox 返回 500

- **现象**：Outlook 回源自检显示可用，但主动读取 Inbox 返回 500。
- **已确认根因**：生产后端 traceback 显示 `FOR UPDATE is not allowed with DISTINCT clause`。读取到的消息进入询盘关联逻辑后，SQLAlchemy 生成了 PostgreSQL 不支持的 `SELECT DISTINCT ... FOR UPDATE` 查询。问题发生在本地消息处理阶段，不能归因于 Outlook 授权失效。
- **为何没被提前发现**：相关隔离测试使用 SQLite；它与 PostgreSQL 的锁定及 SQL 语法行为不同。仅通过 SQLite 测试不能证明该查询可在 PostgreSQL 执行。
- **处理与状态**：代码移除不必要的 `DISTINCT`，保留询盘行锁，并增加 PostgreSQL 方言 SQL 编译检查。相关离线回归测试通过；用户后续反馈原有问题已修复。尚无独立记录证明 PostgreSQL 并发行为已完整验收。

### Gmail 主动断开后无法重新开始授权

- **现象**：点击“开始授权”后提示账号已初始化，但页面仍显示账号尚未创建；日志显示本地账号初始化接口返回 200，之后没有发起 Gmail OAuth start 请求。用户说明此前主动断开过连接。
- **代码机制**：初始化接口过去会直接返回已有 Gmail 账号，即使该账号状态是 `revoked`；授权范围内的账号列表则排除 `revoked` 账号。前端因此可能反复进入初始化分支，而无法进入 OAuth start。用户的断开操作和日志与这一机制吻合；当时没有单独提供账号状态的数据库证据。
- **辅助问题**：旧前端不论工作台刷新是否成功都显示初始化成功，容易误导排查。Gmail 授权原本是在当前标签页跳转，不是打开弹窗。
- **处理与状态**：针对有匹配 grant 的已撤销账号恢复待授权状态，不恢复旧凭据；前端在刷新成功后继续发起 OAuth。用户后续成功到达 Google 回调，证明之前卡在初始化阶段的问题已得到改善。缺失 grant 的账号不会被自动恢复权限，仍需单独诊断。

### Gmail OAuth 回调失败

- **现象**：用户重新授权后，回调返回 502，页面显示“Gmail OAuth 授权失败”；另一次 Google 返回 `access_denied` 时，回调因缺少 `code` 返回 422。
- **已确认事实**：OAuth start 成功；至少一次回调到达项目后发生错误。旧代码把 token 交换、scope 检查、身份查询、Pub/Sub topic 与 Watch 创建等多个失败统一映射为相同的 502，现有日志不能确定具体失败阶段。拒绝授权被 422 处理是已确认的回调处理缺陷。
- **有依据但未证实的假设**：当次 Google 返回的 scope 不含 `openid`，代码却调用 OpenID UserInfo 获取身份。缺少身份 scope 可能造成失败，但没有该次 Google 响应状态，不能把它写成已确认根因。
- **处理与状态**：代码增加 `openid` scope、拒绝授权处理，以及仅记录阶段和 HTTP 状态码的诊断日志；相关离线测试 24 项通过。尚未获得用户部署新版本和真实授权成功的证据。
- **安全教训**：旧访问日志中出现过 OAuth callback 的 code 和 state。代码已针对应用及内置 Nginx 增加回调日志保护；外层反向代理、CDN 和其他日志系统仍须单独检查，不能假定所有位置均已保护。不得在验收记录中保存完整回调 URL、token 或 state。

## 2. 为什么反复出现问题

1. **验证环境与生产不一致**：SQLite 单元测试覆盖了业务路径，但没有验证 PostgreSQL 对锁和查询语法的实际约束。SQL 编译检查有帮助，但不代替真实 PostgreSQL 执行与并发测试。
2. **只覆盖首次接入，遗漏状态转换**：正常创建和首次授权不等于断开、重连、历史记录、权限缺失等状态均可用。已撤销记录的返回和列表过滤形成了跨接口矛盾。
3. **把多个步骤视作一个授权动作**：OAuth 跳转、回调、token、授权范围、身份、Watch、凭据持久化分别可能失败；一条泛化错误既无法确定归属，也延长了定位时间。
4. **真实成功路径不代表错误分支已覆盖**：Google 拒绝授权、缺少 scope、外部 API 失败等没有得到足够明确的产品处理和验收。
5. **状态与证据混淆**：自检通过只证明它检查的步骤；容器健康、测试通过、授权已发起都不能替代完整的真实入站验收。早期对时间字段的怀疑也说明推测应始终与生产 traceback 区分。
6. **安全可观测性不足**：没有安全的分阶段诊断，又存在回调查询参数进入访问日志的风险，导致排障和敏感信息保护同时承压。

这些是本次证据支持的工程过程问题；不能推断未观察到的故障次数或将所有渠道故障归结为同一个原因。

## 3. 后续质量门禁

- **分层测试**：保留 SQLite 快速测试，增加独立临时 PostgreSQL 的迁移、关键查询和消息关联集成测试；覆盖并发和事务回滚。绝不能对生产数据库运行破坏性测试。
- **渠道生命周期矩阵**：每个渠道至少覆盖首次授权、拒绝授权、取消、断开、重连、授权过期、账号不匹配、历史账号/权限记录缺失和重复操作。
- **逐阶段可观测性**：区分 OAuth start、callback、token、scope、身份、Watch/订阅、落库和消息处理；记录安全错误分类及状态码，不记录敏感查询参数、凭据和消息正文。
- **明确验收证据**：分别记录代码和离线测试、目标镜像与 PostgreSQL、真实渠道和浏览器的结果；未执行项标为未验证。自检需明确检查范围。
- **真实环境变更**：先准备备份、回滚和可恢复的部署步骤；部署及真实授权由用户决定和执行。部署后依次验证授权、消息入站、重复读取、断开重连和失败提示，避免直接使用生产数据做破坏性测试。
- **安全检查**：检查所有代理的 OAuth callback 访问日志策略；对外分享日志前移除完整 URL、code、state、token、cookie、邮箱及正文。

## 4. 当前待验证事项

- 部署包含最新 Gmail OAuth 修改的镜像后，使用新一轮授权验证 Google 回调、账号身份、Watch 和真实入站；如果失败，收集脱敏的 `gmail_oauth stage=... status=...`。
- 在隔离 PostgreSQL 上实际执行询盘关联测试，并验证并发行为。
- 核查生产外层代理是否记录 OAuth callback 查询参数；按实际日志保留策略处置历史敏感日志。
- OAuth state 当前为进程内存储，多 worker 之间的撤销与 state 失效不保证同步；若采用多 worker 或多实例，需要共享状态或持久版本校验方案。
